The keep-awake control turns sleep off with `pmset`, so every way a run ends must turn it back on. The `pmset` and admin-prompt calls live in `crates/tidewatch-core/src/amphetamine_lid.rs` (`admin_command`, `helper_script`, `osascript_args`). Check `man pmset` before you change a key, and test each path against a fake. For screenshots, set `TIDEWATCH_FAKE_AMPHETAMINE` to `off` (no activation) or to `toast`, `hour`, `end` or `notice` (that toast, on the fake system).

## Lid-closed mode
- Owner's decision, 2026-10-25: Touch ID is asked once per Tidewatch run, not on every activation. The owner's words: "I would've expected it to ask me once when I first use it and then not ask me again until I restart tidewatch or something". The first start in a run asks for Touch ID. A root helper then stays up, serving only on, off and the deadline over a socket in Tidewatch's state folder (created 0600, owned by the user). It restores sleep at the deadline, on off, and when the Tidewatch pid it was given is gone, then exits. Quitting or restarting Tidewatch ends it, so the next run asks again. If the helper is missing or does not answer, fall back to the prompting path. Once PR #168 is on main, a release that replaces the helper does not need the Settings setup again: the next start's one admin prompt replaces the older helper (see tidewatch-release). Until a Mac runs two activations in one run, the once-per-run behavior is Not verified.
- Turning it on asks for the admin password once, and only while the Touch ID helper is missing. A helper started with that prompt owns the restore.
- Before you tell the owner a setup step stops a prompt, read the installed helper file and the start code that runs with it. On 2026-10-25 a "one-time setup" answer was wrong: the prompt came back on every start. Never leave the owner a manual setup step the app can run itself.
- Before you debug a password prompt, check the helper. If `/Library/PrivilegedHelperTools/tidewatch-amphetamine` and `/etc/sudoers.d/tidewatch-amphetamine` are both missing, the Mac was never set up, and every start takes the password prompt. An older helper is the other cause: the file is there but from an earlier build, so every start asks for the password and then skips installing the new helper. The start's password prompt now installs the new helper too, so the owner does not need the Settings row (General, Keep awake, Set up) for this. Not verified until the owner's Mac runs the 0.1.25 start. PR #147 (open on 2026-10-25, not yet merged when this was written) changes the first start. On a Mac with a fingerprint reader and no helper, one admin prompt installs the helper and starts lid mode, and every later start uses Touch ID. A Mac with no reader still asks for the password each time and installs nothing. Check main before you rely on either.
- Owner report, 2026-10-25, on 0.1.21: the button waited 30 to 40 seconds before the password prompt appeared. On 2026-10-25 a worker ruled out queueing: `Jobs::spawn` starts one thread per job with no pool, nothing slow runs before `osascript`, and a test that blocks 16 other jobs still starts the prompt within 2 s. Whether the rest of the wait is the dialog itself or `osascript` is unknown. Ask the owner to time the gap from click to dialog on a real Mac before you call it fixed.
- The helper turns sleep back on when the timer ends, when the user clicks Turn off (no second prompt), and when Tidewatch quits or crashes.
- At the next launch, a sleep-off that Tidewatch itself left over from its last run shows a notice and is turned back on. Only a sleep-off Tidewatch wrote counts: a `caffeinate` or `pmset` setting the owner made by hand is never touched, even while it runs.
- The real password prompt and the real sleep setting are checked by the owner on a Mac after release. Until then, list them under Not verified.
- Owner report, 2026-10-24, on a real Mac: the prompt asks for the account password, not Touch ID, and the button sometimes waits a moment after the password is entered. The button flips only after a wait loop, which pauses 500 ms between checks (`SETTLE_EVERY` in `crates/tidewatch/src/amphetamine_glue.rs`). The length of that wait on a real Mac is not measured. The prompt is the `osascript ... with administrator privileges` call in `osascript_args` (`crates/tidewatch-core/src/amphetamine_lid.rs`). The claim that Touch ID cannot work in that dialog was never checked against Apple's docs: check before you tell the owner it is impossible. On 2026-10-25 a worker checked the Rust side and found no way to put the Touch ID sheet in Tidewatch's window: `objc2-local-authentication` 0.3.2 has no `LAAuthenticationView`, `coreauthd` draws the sheet outside the app, and `osascript` cannot attach it either. That is one worker's finding, so check it again before you call an in-window sheet impossible.
- The `amphetamine_helper` timing test went red once on an Ubuntu run (2026-10-26) for a PR that did not touch keep-awake code. The same commit had passed on its PR run, and one rerun passed. A second red on that test is a regression: fix its timing before you rerun again.
- Touch ID for Amphetamine was built as #133 on 2026-10-24, with a one-time setup in Settings. This item is no longer open: read #133 and the Settings page before you change the design.
- While the start prompt (password or Touch ID) is open, Tidewatch loses focus to it, and the quake drop-down must not hide on that blur. Hold hide-on-blur until the prompt ends, then bring the window forward once, and only if it was the active app when the owner pressed the button. PR #158 does this. No live prompt had been tried when written, so list it under Not verified until the owner tries one on a Mac.
- The `amphetamine_lid` tests are timing-flaky under heavy parallel load. When only they fail in a full `cargo test --workspace --locked` run, rerun once before you debug them.
- The `amphetamine_lid` tests in `tidewatch-core` are timing-flaky under load. On 2026-10-25 the first full run failed two of them, a run of that module failed three, and the next full run passed. Run the module alone, on the branch and then on main, before you call a failure real: one that passes alone is noise under load, and one that persists is a regression.
